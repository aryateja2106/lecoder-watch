# The LeSearch AI reset — one repo, one spec, one install

Dated 2026-09-06. This is the plan for moving two years of work under one name, in one
repository, with one canonical product document, without breaking a single installed
daemon or paired phone. It answers the question Arya asked while looking at the GitHub
org: *"I don't know whether we have a Mac app, a Watch app, an iPhone app."* We have all
three. Nothing on the org says so.

`PRODUCT.md` next to this file is the durable half: what the product is. This file is
the migration: what moves where, what is archived, in what order, and what must not
change.

## 2. Decisions

### 2.1 One repository: `LeSearch-AI/mesh`

Reuse the name that is already public. Every README, the landing page, the TestFlight
notes and the org description point at `github.com/LeSearch-AI/mesh`; creating
`lesearch-mesh` or `mesh-monorepo` next to it would be a fourth name for the same thing.
The current snapshot repo becomes branch `archive/snapshot-2026-08-21`; the new `main`
is the reorganised tree below, imported from `release/lesearch-mesh-0.6` after it lands.

**History: clean slate.** The new `main` starts from one commit ("LeSearch Mesh 0.6 —
imported from lecoder-watch") with the reorganised layout. The full history stays
readable in `aryateja2106/lecoder-watch`, which is archived (and made private) the same
day, not deleted. Two years of branch names and WIP checkpoints do not need to follow
the product into its public home.

### 2.2 What is frozen, whatever the repo is called

| Thing | Value | Why it cannot change |
| --- | --- | --- |
| Install URL | `github.com/LeSearch-AI/mesh-install/releases/latest/download/install.sh` | Compiled into `PairMachineView`, `LocalDaemon.swift`, `DaemonCapabilities.swift`, `doctor.ts`. Every installed daemon upgrades from it. |
| Install prefix | `~/.mesh` | Every hook, token, host file and service on every machine. |
| Service labels | `ai.lesearch.meshd`, `ai.lesearch.rmux-bridge` | launchd and systemd units on every machine. |
| Bundle ids | `com.lecoder.meshwatch.*`, `com.lecoder.meshdesktop` | Apple never lets a deleted App ID be reused; `…watchkitapp.complication` was already burned. |
| URL scheme | `meshwatch://` | The only scheme the phone registers; it is what the pairing QR carries. |
| Xcode target names | `MeshWatch`, `MeshDesktop`, `MeshWatchWidgets`, `WatchWidgets` | Schemes, entitlements, provisioning. Renaming buys nothing and costs a signing afternoon. |
| Ports | `8899`, `7820` | Every paired phone. |

Everything else is a path in a repository and can move with `git mv`.

### 2.3 Naming rules

Exactly as `PRODUCT.md` section 2. The short version: **LeSearch AI** makes **LeSearch
Mesh**; the daemon is `meshd`; the CLI is `mesh`; `MeshWatch` and `lecoder` appear only
where Xcode or Apple force them, never in a README, a commit subject, a landing page or
a repository name. `lesearch` alone is the retired Rust product and is not reused.

**What does not come along:** `build/` (untracked), `references/` and `reference-video/`

`static-landing.png`, `Lesearch-Logo-light.png` (a raster of the SVG), `index.md`,
`PROGRESS.md`, `HANDOFF.md`, `MEMORY.md`, `TASKS-2026-09-01.md`, `skills-lock.json`,

**Why `apps/` and not one directory per platform at the root:** a visitor to the org
should see, in the first screen of the tree, that there is an iPhone app, a watch app, a
Mac app, a daemon, a CLI, an installer and a website. Seven words at the root do that;
twenty-six do not.

## 5. The migration, in order

Each step is one agent task with its own gate. Nothing starts before step 0.

0. **Land 0.6.** PR #124 merges (Arya merges; agents never do). The reset branches from
   that commit, so no in-flight work is moved twice.
1. **Reorganise in place** on a branch of this repo (`reorg/monorepo`): `git mv` per
   section 3, then update every path that names a directory — `project.yml` sources,
   `install.sh` and `package-mesh-install.sh` payload paths, every `scripts/check-*.sh`,
   `ci_scripts/`, `.github/workflows/ci.yml`, `CONTEXT.md`'s "where things live" table,
   `docs/README.md`. **Gate:** `xcodegen generate`; both schemes build for generic
   simulator destinations; `sh scripts/check-all.sh` green;
   `sh scripts/check-product-spec.sh` green; `sh scripts/package-mesh-install.sh` produces
   a tarball whose `install.sh --list` matches today's.
2. **Prove the installer from the new tree** on this Mac against a test prefix
   (`MESH_HOME=/tmp/mesh-reset MESH_LABEL_PREFIX=ai.lesearch.test`), then
   `--uninstall --purge`, and confirm nothing under the real `~/.mesh` changed. This is
   the step that protects every installed machine.
3. **Import into `LeSearch-AI/mesh`:** rename the existing `main` to
   `archive/snapshot-2026-08-21`; push the reorganised tree as a single commit on a new
   `main`; branch protection on; the factory labels and `docs/factory/` come along.
4. **Point everything at it:** README links, the landing's GitHub link, the TestFlight
   notes, `CONTEXT.md`. The install URL does not change (section 2.2).
5. **Org front door:** rewrite `.github/profile/README.md` to list the surfaces with one
   screenshot each; pin `mesh` and `mesh-install`; archive per section 4.
6. **Archive `lecoder-watch`** (private first, then archived). Close or move the open
   PRs first: #126 (voice), #125 (40 mm watch), #120 (notifications) are real fixes and
   are re-based onto the new `main`; #119 (local inference) and #121 (Docker) wait for
   their decisions; #4, #118, #122, #127 are superseded or documentation and close with a
   note.
7. **Worktrees:** `git worktree prune` after step 6; the `~/.omnara`, `~/.codex` and
   `.claude/worktrees` entries are other agents' and are removed by their owners.

## 6. The permissions window

Yes, it can be edited, and cheaply: the window is already a data-driven front end to
`/doctor`, so the reference design (required-for-what-you-use / other, per-feature
attribution, an honest *can't check* state, per-row *Request*) is four additive fields
on the daemon and a grouping change in one SwiftUI file. The full specification is
`PRODUCT.md` section 8. Three files change: `doctor.ts`, `LocalDaemon.swift`,
`PermissionsView.swift`; `check-mesh-doctor.sh` gains one assertion. The phone's setup
section reads the same fields in a following slice. It is one factory item, after 0.6.

## 7. Needle, in three slices

1. **Measure on the Mac, no app code.** `pip install cactus-needle`; run the bundled
   `wearable` environment and ten of our own phrases through the `macos-arm64` CLI;
   record accuracy, confidence, latency and RAM in `docs/results/`. Decide from the
   numbers.
2. **Catalogue and suite.** `intent/mesh-tools.json` generated from the daemon's
   capabilities and the CLI verbs; `intent/cases.jsonl` with real phrases;
   `scripts/check-intent.sh` runs them through the CLI. Fine-tune only if slice 1 says
   the base model needs it.
3. **The watch.** XCFramework from the static libraries, the confidence gate, the risk
   classifier in the path, a stub for the watch simulator. Verified on the physical
   watch; the Mac CLI suite is the loop gate.

Full design: `PRODUCT.md` section 9.

## 8. What this plan does not do, and the risks

- It does not rename Xcode targets, bundle ids, the scheme, the install prefix or the
  install URL. Section 2.2 is the list; a reviewer's first job on the reorg PR is to
  diff those seven values against `main`.
- It does not rewrite the apps, the daemon or the installer. It moves files and updates
  the paths that name them. If step 1's gate needs a code change beyond a path, stop
  and hand back.
- It does not decide the local-runner question (`mesh-code` versus `dsh`), the Mesh
  Apps tier, or whether the Mac app ships as a cask or inside the installer. Those stay
  in `PRODUCT.md` section 12 for Arya.
- **Risk: the move happens while a checkpoint branch diverges.** Every branch not
  re-based onto the reorganised `main` becomes a manual merge. Section 5 step 6 names
  which ones are worth it.
- **Risk: `check-all.sh` passes without compiling the apps** (recorded 2026-09-02). The
  reorg gate therefore lists the `xcodebuild` runs explicitly rather than trusting the
  suite.
