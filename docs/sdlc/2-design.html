Design: agree what it is and how it looks

Before anyone builds, one short document says what the feature is and how it should look, written under your rules. For the app's look, nobody has ever written that document, and customers can tell.

  • Reads the accepted intent from Stage 1
  • Commits a spec in openspec/changes/<slug>/

Where we are

  • Done The product spec is checked against the code (scripts/check-product-spec.sh)
  • In progress The design theme is written as a spec (openspec/changes/design-theme/proposal.md); the draft intent exists you B-06 checked 2026-09-27
  • Not started Every spec names the intent it came from (part of B-06)

  • Not started One file holds the app's colours and spacing (Shared/Theme.swift, part of B-09)

Each line is checked by sh scripts/check-sdlc-status.sh.

What the playbook says

(Numbers in brackets are the playbook's section numbers.)

  • A spec turns an accepted intent into requirements and a design. (2)
  • It is written under the company's own skills: brand, security, compliance and UX. (2)
  • So your rules are applied while the spec is written, not discovered later in review. (2)
  • The product owner reviews the spec against the intent; a tech lead joins when the risk is higher. (2)
  • Measure how long an intent takes to become a spec, and how much the spec changes after the plan. (2)

Orange means three things today. In the app it means "an agent needs you" (docs/product/design-system.md). In chat it is Claude's colour, which paints your own message bubble (iOS/AgentChatView.swift; the picture is docs/product/shots/iphone-chat.png). On the website it is the buy button (web/index.html). The one signal that matters most looks like decoration.

The 20 design questions that settle all of this are written down, with example answers, in intents/INTERVIEW.md. A shorter version sits in the draft design intent, intents/2026-09-27-bring-my-design-theme-into-the-app.md. They are not copied here, so they cannot drift.

The gap

  • The design intent is written, but only as a draft; you have not accepted it, so no spec may start.
  • There is no design spec (openspec/changes/design-theme/proposal.md), so nothing you have approved says what the app looks like.
  • There is no token file (Shared/Theme.swift), so every screen types its own colours and spacing.
  • Nothing ties a spec to its intent, and light versus dark was never decided.
  • The UI skill names colour roles but no palette, so agents fall back to Apple's defaults.

How you take part

  1. Read the draft design intent, intents/2026-09-27-bring-my-design-theme-into-the-app.md. It is written in your words. About 5 minutes.
  2. Answer the 20 design questions, one at a time, with an agent asking, in the Claude Code desktop app, in a session opened on this repo (intents/INTERVIEW.md). Pick an example answer, combine two, name an app you like, or show a picture. About 30 minutes.
  3. Accept the intent yourself: change status: draft to status: accepted. Only you may do this (intents/README.md). Then an agent writes the spec in openspec/changes/design-theme/, and you read and approve it (B-06).
  4. Later, look at a before-and-after screenshot pair of one screen in your colours and say yes or no (B-09). A few minutes.
  5. Decide which feature, if any, you want in Rust, in intents/2026-09-27-typescript-and-rust-module-boundaries.md (B-17). About 20 minutes. The review's advice is "not yet" (references/agent-git.md).

Run the design interview with me one question at a time, then draft openspec/changes/design-theme/ from my answers only. Do not choose a colour, font or mode I did not choose; write open where I have not decided.

A worked example from our own history

Orange picked up three meanings, one at a time, and nobody decided any of them. The app already used orange for "needs you". On 2026-09-04 the new chat screen (iOS/AgentChatView.swift) gave Claude an orange, and that colour went onto your own messages. On 2026-09-22 the relaunched landing page (web/index.html) made orange its one button colour. The clash was found on 2026-09-27, while mapping the repo for this site.

Each choice made sense on its own. A spec written under a brand rule would have caught the clash before any of them shipped, because the rule would have said what orange is for.

For agents

When proposing a change, validate it, then run the intent and product-spec checks and the loop gate:

openspec validate design-theme
sh scripts/check-intents.sh
sh scripts/check-product-spec.sh
./.claude/scripts/gates.sh fast

Healthy gate line (seen 2026-09-27):

FACTORY_GATES: level=fast status=GREEN passed=2 failed=0 failing=none skipped=none misconfigured=none
  • Colour roles already relied on: orange means needs you, red means destructive or error, green means working (docs/product/design-system.md). A new accent that is orange or red re-decides these; do not do it silently.
  • Interaction rules pinned by existing checks must survive any restyle (docs/product/design-system.md).
  • Never choose a colour, font, mode or glass rule Arya did not choose. Write "open" instead. Never set status: accepted on an intent.
  • Protected: .agents/** (including the UI skill), AGENTS.md, CLAUDE.md. Edit them only with Arya in the session.
  • Serialized, one agent at a time: Shared/Models.swift, Shared/MeshClient.swift, install/payload/meshd/server.ts, project.yml (AGENTS.md).
  • Never embed an image on this site, never link Reference-images/, and never copy colour values out of screenshots.
  • Skills to load: openspec-propose, spec-driven-development, frontend-ui-engineering, and for UI work meshwatch-ui-taste (partly stale).
