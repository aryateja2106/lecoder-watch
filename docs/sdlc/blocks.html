The blocks, in order

A block is one piece of work small enough to finish and prove on its own. Work top to bottom, one at a time.

How a block works

One intent leads to one change, and that change has one check that fails without it. The change arrives as a draft pull request, and a human merges it, never an agent. Each block below shows its stage, its size (S is one day or less, M is up to three days), who signs it off and what it waits for. Its status line carries a proof, so the line turns green only when the repo really changes. Lines marked you are yours to act on. The full text of every block, with the files it touches and what happens if you say no, is in docs/sdlc/BLOCKS.md.

There are two lanes that run at the same time: yours, and the agents'. Inside each lane, work top to bottom. To answer a block, reply in chat (the Claude Code desktop app, in a session opened on this repo) with its id and one word, for example "B-04 yes" or "B-15 option a". Only a yes you type in chat counts.

Later, and why later

These came up and were left out on purpose. Each one returns as its own intent when the reason below stops being true (BLOCKS.md).

  • A separate project copy per agent (worktrees). It helps several agents on one machine, not across machines. The ROADMAP.md "Later" list isolates agents a different way (each agent gets its own Unix user and its own daemon), not with worktrees. Done properly, worktrees are too big for a block.
  • Agent evals in CI and a CI-health control band. A real eval runs an agent on paid model calls with a key in a public repo's workflow, and it only pays off once agents run unattended on a green CI.
  • A plan section inside run records. A plan written at the end of a run cannot prove it came first; the charter's plan-before-code rule replaces it.
  • Per-device tokens. They touch pairing and sign-in, the most sensitive code, so they need their own intent.
  • A read-open, write-gated proxy for apps agents build. Only if the app-serving intent says those apps need a backend at all.
  • A secrets-in-diff hook, and the false alarms in .claude/hooks/block-merge.sh. Both live in a protected folder, and they are worth doing after the first security baseline shows what it finds.
  • Rules for the empty "architecture" gate. No rule is known yet to put in it.
  • Agent triage in CI, on-call chat, managed settings. There are no customers, no pager and no second person yet.
  • The factory:* labels and a re-triage of the open issues. The labels were never created (.factory/scripts/bootstrap-github.sh was never applied), and the issues date from 2026-08-27/28; re-triage them after your intents are accepted.
  • Skills clean-up. Skills are advice only; prune one when a run shows it being ignored.
  • The other "Now" items in ROADMAP.md (terminal gestures, hold-to-talk, model picker, Mac permissions at setup, friendly app addresses). They are product features, not lifecycle work, and each enters as an intent.
  • The brain probe order in install/payload/meshd/brain.ts (see BLOCKED.md). A product slice, not lifecycle work.
  • CONSTRAINTS.md. docs/product/PRODUCT.md calls it "the floor", but no such file exists at the repo root. Flagged, not planned.
  • The dormant .claude/hooks/stop-published.sh. It is not wired, and the publish mission it served has ended.
