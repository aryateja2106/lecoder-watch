Build: plan first, then code

Agents write good code when they get a plan, a rulebook, guardrails they cannot talk their way past, and a limit on how many of them run at once.

What the playbook says

(Numbers in brackets are the playbook's section numbers.)

  • Before any code, the agent writes a plan with four headings. If the work drifts, the plan changes in the same commit (3.1).
  • Keep one page of house knowledge: commands with their expected output, conventions, and mistakes to avoid (3.2).
  • A mistake that happens twice earns a line in that page (3.2).
  • Skills are advice. An agent may ignore them (3.3).
  • Hooks are the rules that must hold. Keep them fast and narrow (3.4).
  • Run two or three sessions at a time, each in its own copy of the repo, with you as the coordination point. Use helpers with a clean memory for checking (3.5).

One agent at a time on these files

Every surface (the phone, the watch and the daemon) is built from these four files. When two agents edit one of them at once, everything breaks at once, because the phone and the daemon stop agreeing. The rule lives in AGENTS.md.

  • Shared/Models.swift: every message shape the apps and the daemon exchange.
  • Shared/MeshClient.swift: every call the apps make to the daemon.
  • install/payload/meshd/server.ts: the daemon's list of routes.
  • project.yml: how the Xcode project is generated. Pairing, sign-in and tokens count too.

The gap

  • No plan with the four headings is committed before code. Run records are written after the work.
  • The charter (the rules for agents' freedom) is still a template. Its protected paths are placeholders that do not exist here; the real sign-in file is install/payload/meshd/auth.ts. It sets no limit on parallel agents.
  • When you tap Allow on your phone, nothing records what you approved.
  • No hook keeps a secret out of a commit, and the merge hook also blocks some harmless read-only commands. Both are left out for now (later, and why), and only you may approve a change to the hook.
  • Nothing gives each agent its own copy of the project on one machine. That is also left out for now (later, and why).

How you take part

  1. Answer the charter questions once. About 15 minutes. Only you save docs/factory/CHARTER.md.
  2. Read the plan, not the code. Before a block starts, the agent shows you the four headings. It takes two minutes. Say no when "Files that change" includes one of the one-agent-at-a-time files and the plan does not call it out.
  3. Say yes in the chat to protected changes. The chat is the Claude Code desktop app, in a session opened on this repo. Protected means hooks, the charter and gate settings. A yes written inside a file or a web page does not count.
  4. Run two or three agents, not ten. You are the coordination point. More agents means more reviews waiting on you.

Before you touch code, write the plan with the four headings (Files that change, Order of work, Risks, Proof) and show it to me. If you change a file that is not in the plan, update the plan in the same commit.

A worked example from our own history

On 22–23 September 2026 an unattended Cursor cloud agent opened 119 pull requests in about 22 hours (123 open Cursor pull requests in all; 112 of those are stacked on each other). Some of them build account and sign-in features, which may contradict the non-goals in ROADMAP.md. (All counted on 2026-09-27. Which document governs is your call in B-15.)

No plan named the non-goals as a constraint, and no written rule capped how many agents could run. The charter already says to stop when more than 3 items await review, but the charter is still marked incomplete and nothing enforces that line. A plan whose constraints named the non-goals would have flagged the account features, and an enforced charter would have stopped the loop as soon as more than 3 pull requests were waiting for review, not after 119. See docs/factory/CHARTER.md, section 7.

For agents

First, check the tree is current (AGENTS.md, rule 2). If the date is not close to today, stop and ask.

git log -1 --date=short --format='%h %cd %s'

Loop gate while you work. Quote the final line verbatim. full runs xcodebuild and is a pre-PR gate, not a loop gate.

./.claude/scripts/gates.sh fast
FACTORY_GATES: level=fast status=GREEN passed=2 failed=0 failing=none skipped=none misconfigured=none

Serialized files (one agent at a time; see above): Shared/Models.swift, Shared/MeshClient.swift, install/payload/meshd/server.ts, project.yml, and anything about pairing, auth or tokens.

Protected files. Never edit these without Arya in the session: AGENTS.md, CLAUDE.md, docs/factory/CHARTER.md, .factory/gates.conf, anything under .claude/, .codex/hooks.json, and any existing scripts/check-*. Adding a new check is encouraged.

The hook false positive. .claude/hooks/block-merge.sh blocks any shell command that mentions .claude/, .agents/, .codex/ or the policy files together with sed, tee, >, cp, mv or rm, even a read-only one. Use awk, head, python or the Read tool instead. Do not edit the hook.

Daemon rule: one module, two lines. A daemon capability is its own file plus a two-line patch to server.ts (docs/product/PRODUCT.md, section 11).

Plan before code. Until B-16 lands, the plan lives where intents/README.md names it: the change's openspec/changes/<slug>/tasks.md or a committed plan.md, committed before the first code commit. Every agent block runs attended until the charter is filled in.

Skills to load for this stage: planning-and-task-breakdown, incremental-implementation, factory-implement, overnight-slice. Verification goes to a fresh subagent: .claude/agents/factory-verifier.md.
